# m5-uarch 導讀

這份文件是寫給剛接觸這個題目的人看的。讀完之後，你應該可以用自己的話在面試裡講清楚：這個專案在解決什麼問題、
怎麼解決的、為什麼可以相信它量出來的數字。

## 一、它在解決什麼問題

電腦的處理器（CPU）執行每一道指令都要花時間，但每種指令花的時間不一樣：加法很快，除法很慢。而且現代處理器
一次可以同時做很多道指令。寫編譯器、寫高效能程式、或是研究處理器的人，都想知道兩件事：

1. **每一道指令要花幾個「週期」**（週期是處理器的節拍，M5 的大核心一秒大約 45 億拍）。
2. **處理器裡面那些暫存區有多大**（一次最多可以同時處理幾道指令、有幾個加法器……）。

Apple 不公布這些數字。以前有人替 M1 量過，但那些工具需要系統管理員（root）權限。這個專案做了兩件事：

- 寫了一個**不需要 root** 就能量測的工具。
- 用它量了 **Apple M5**，把大核心和小核心的數字都整理成表格公開。

## 二、八個關鍵觀念

### 1. 處理器內建的「計步器」

macOS 會幫每個程式記錄它走了幾個週期、執行了幾道指令，而且大核心和小核心分開記。程式可以讀自己的紀錄。

> 比喻：像手機的計步器。你不需要醫院的儀器（root 權限），自己的手機就知道你今天走了幾步，
> 而且還分開記「在操場走的」和「在走廊走的」。

對應程式：`src/counters.c`。

### 2. 相依鏈：量「延遲」的方法

想知道加法花多久，不能只做一次（太短，量不到）。做法是讓每一次加法的結果當成下一次加法的輸入，
串成一條鏈，這樣處理器沒辦法同時做，只能一個接一個。跑一百萬次，把總週期數除以次數，就是一次加法的延遲。

> 比喻：接力賽。每一棒都要等上一棒把棒子交過來才能跑，所以全隊的總時間除以人數，就是每個人跑一棒的時間。

對應程式：`tools/gen_insns.py` 的 `_one_chain`，以及 `src/insn.c`。

### 3. 吞吐量：量「一次能同時做幾個」

反過來，如果每道指令之間互不相干，處理器就可以同時做好幾個。把很多道互不相干的同一種指令排在一起，
看每個週期能完成幾道，就知道有幾個「窗口」在處理這種指令。

> 比喻：超商結帳。延遲是「一位客人結帳要多久」，吞吐量是「開了幾個櫃台」。
> 一位客人要 3 分鐘，但如果開 3 個櫃台，平均每分鐘可以結完 1 位。

### 4. 量兩次、相減

每次讀計步器本身也要花時間（大約 600 個週期）。所以同一段程式跑 n 圈和 2n 圈，兩個數字相減，
讀計步器的成本就抵銷了，剩下的剛好是 n 圈的成本。

> 比喻：想知道一箱蘋果裡一顆蘋果多重，但只有一個連箱子一起秤的秤。秤「箱子＋10 顆」和「箱子＋20 顆」，
> 相減就是 10 顆的重量，箱子的重量自動消失。

對應程式：`src/measure.c`。

### 5. 怎麼知道這一次量得「乾不乾淨」

這台電腦同時還有別的程式在跑，系統隨時可能打斷我們。但我們知道迴圈「應該」執行幾道指令（這是我們自己產生的程式）。
如果計步器說執行的指令比應該的多，多出來的就是作業系統插進來做的事，這一次就作廢。
另外，如果大核心和小核心的計步器同時都有增加，代表中途被搬到另一種核心，也作廢。

> 比喻：考試時監考老師數每位考生交了幾張答案卷。你明明只發了 3 張，收回 5 張，就知道有人動過手腳，這份不算。

### 6. 用兩個「塞車點」量暫存區的大小（Henry Wong 的方法）

處理器可以提前做後面的指令，但能提前多少，取決於它內部的等候區有多大。做法：放兩個很慢的操作
（從記憶體深處拿資料，要等幾百個週期），中間塞 F 道填充指令。如果等候區裝得下「第一個慢操作＋F 道填充＋
第二個慢操作」，兩個慢操作就會同時等，總時間是一個慢操作的時間；裝不下，第二個就得等第一個做完才能開始，
總時間變兩倍（理想情況；實測大約 1.7 倍）。慢慢增加 F，時間突然跳起來的那個 F，就是等候區的大小。

> 比喻：餐廳候位區。兩桌大菜都要等很久。如果候位區夠大，兩桌客人可以同時進來點菜、一起等；
> 候位區太小，第二桌客人連門都進不來，要等第一桌吃完才能點。

對應程式：`src/exp_window.c`。

### 7. 處理器會「猜」，而猜會騙過量測

M5 的大核心很聰明：

- 如果一個「讀記憶體」的指令每次都讀到同一個值，它就直接猜那個值，不等真的讀完。
  結果用傳統方法量「讀記憶體要多久」會量到 0.34 個週期（其實是 3）。
- 如果資料看起來像記憶體位址，它會提前把那個位址的資料也抓進來。
- 如果「條件選擇」指令的條件從來沒變過，它會直接當成條件不會變。

所以工具必須故意讓資料「不好猜」：讀記憶體時走一個 509 個點的隨機路線、存索引而不是位址、
每次量測之間把條件反過來跑一下。這些「猜」的行為本身，工具也另外設計實驗把它們量出來，寫在結果裡。

> 比喻：老師出考題想測學生會不會算，但如果每次都出同一題，學生直接背答案就好，測不出計算能力。
> 所以要換題目；同時也順便記錄「這個學生會背答案」這件事。

對應程式：`src/exp_spec.c`，以及 `src/insn.c` 裡的 `random_cycle`。

### 8. 讓任何人都能送資料進來，而且自動把關

一台 Mac 只能量一顆晶片。想要比較 M1、M4、M5，就得讓別人也能把他們的結果送進來，而且不能花錢架伺服器。
做法是只用 GitHub 本身：

- **送什麼。** 完整結果檔有 370 KB，但一個 issue 最多只能放 65 536 個字。所以不送結果檔，只送「每一輪量到的
  原始數字」，壓縮後變成一段約 42 000 字的文字，使用者執行 `make submit`，貼進 issue 就好。指令的文字說明
  （組合語言、相依鏈）不用送，因為接收端用同一版工具就能重新產生，再用一個「摘要值」（SHA-256）確認兩邊一樣。
- **隱私。** 只複製白名單上的欄位（晶片、機型、macOS 版本、量測數字），電腦名稱、使用者名稱、序號、路徑一律
  不送；任何看起來像路徑或電子郵件的文字，打包程式和檢查程式都會拒絕。
- **自動檢查。** GitHub Actions 讀到 issue 之後，用原始數字重新算一次所有統計值，對不上就退回；再檢查「加法
  一定 1 個週期」這類錨點、P 核不該比 E 核小、跟同一顆晶片的舊資料比有沒有離群值。結果在 issue 底下留言：
  接受、標記待審、或退回。接受的資料自動開成 pull request，但一定要維護者按合併才會進主分支。
- **安全。** issue 內容是陌生人寫的，所以只當「資料」讀，絕不當成指令執行；讀資料的那一段只有唯讀權限，
  有寫入權限的那一段只處理檢查程式自己產生的檔案。

> 比喻：像學校的投稿信箱。投稿的人不用認識編輯，把稿子照格式放進信箱就好；收發室先自動檢查格式、字數、
> 有沒有抄襲（重複），合格的才放到編輯桌上，最後由編輯決定要不要刊登。收發室只拆信、不照信裡寫的話去做事。
> 但收發室擋不住「很用心的假稿」，所以同一個題目要有好幾個人獨立投稿，結果一致才算數，網站會顯示每顆晶片有幾份。

對應程式：`tools/uarch_submit.py`（打包、隱私過濾、解析 issue）、`tools/uarch_validate.py`（所有檢查、
機器人留言）、`tools/uarch_site.py`（多份資料合併成網站資料）、`.github/workflows/submission.yml`。

## 四、跑一次看看

```sh
make                 # 建置
build/uarch info     # 看這台機器的基本資料、計數器能不能用
build/uarch selftest # 檢查「加法是 1 個週期」這類一定要成立的事
build/uarch insn -f mul_x          # 只量乘法
build/uarch structure -e width     # 量管線寬度與運算單元數
make measure         # 全部量三次並合併，寫到 results/local/
make submit          # 打包成 issue 用的文字（會複製到剪貼簿、打開 GitHub 頁面）
make validate        # 用機器人的規則檢查所有已收錄的資料
sh tests/e2e_submission.sh   # 不經過 GitHub，模擬一次完整的 issue 提交流程
```

## 五、面試可能會問的十二個問題

**1. 為什麼不需要 root？別人的工具為什麼需要？**
別人用的是可以自由設定的效能計數器（PMU 事件），macOS 只讓 root 設定。我只用系統本來就替每條執行緒記錄的
兩個數字：週期數和指令數，這兩個一般程式就能讀。代價是看不到其他事件（例如微指令數），那些要靠時間實驗去推論。

**2. 怎麼確定程式真的跑在大核心（或小核心）上？**
QoS 等級只是「請求」，不是保證。計數器是依核心種類分開記的，所以我檢查每一次執行：只有指定那種核心的計數器
有增加、另一種完全沒動，才採用。五次執行約一百零四萬個計時迴圈裡，有 882 個因此被丟掉。

**3. 機器上有別的程式在跑，數字怎麼還能可信？**
我知道迴圈應該執行幾道指令。被中斷的話，作業系統做的事會算在我的執行緒上，指令數就會變多。
指令數超過最小值的執行全部丟掉（公布的資料裡大約 7%）。剩下的結果，不同次執行之間延遲的差異中位數在 P 核心是
0.05%、E 核心 0.2%。

**4. 延遲和吞吐量有什麼不同？**
延遲是一道指令從拿到輸入到產生輸出要幾個週期，用相依鏈量。吞吐量是互不相干的同種指令每個週期能完成幾道，
反映有幾個運算單元。例如 M5 大核心的乘法：延遲 3 個週期，但每個週期可以開始 3 個。

**5. 指令的機器碼是怎麼來的？會不會編錯？**
指令表的機器碼全部由系統組譯器在建置時產生，我的 C 程式只是複製。少數要在執行時才決定內容的指令用自己寫的
小編碼器產生，測試會拿大約 2800 組隨機運算元和組譯器的結果逐一比對。

**6. 你遇到最意外的問題是什麼？**
量「讀記憶體的延遲」時得到 0.34 個週期，比任何運算都快，顯然不合理。追查後發現是處理器會預測載入的值：
我的測試每次都讀到同一個值，它就不等了。改成走 509 個節點的隨機環之後得到 3 個週期。
這件事提醒我：得到一個數字不代表量對了，要用物理上合不合理來檢查。

**7. 重排緩衝區的大小是怎麼量的？**
用兩個會等很久的記憶體讀取，中間塞填充指令。填充指令少的時候兩個讀取會同時進行；多到把緩衝區塞滿時，
第二個要等第一個結束，時間明顯變長（理想上是兩倍，實測大約 1.7 倍）。時間跳起來的那個點就是容量。填充指令換成不同種類（NOP、寫暫存器的指令、
儲存指令……）可以分別量不同的結構。

**8. 這個方法在 M5 上為什麼一開始不成功？**
兩個原因。第一，如果記憶體裡存的是指標，處理器的預取機制會提前把下一筆抓進來，第二個讀取根本不用等，
所以看不到時間跳起來；改成存索引就好了。第二，小核心的時脈不固定（公布的五次執行，各自的中位數在 2.0 到 3.0 GHz 之間），
而記憶體延遲是固定的「時間」不是固定的「週期數」，所以要把測試和對照組交替執行、只比較同一時脈下的比值。

**9. 怎麼驗證結果是對的？**
四層。一是「基準點」：加法 1 個週期、比較加條件遞增 2 個週期，任何 ARM 處理器都必須成立。二是每次量測都核對
指令數。三是實驗內建對照組，例如融合測試裡放兩組不可能融合的指令，結果要接近 1.00（實測 1.00 到 1.03）。四是和別人對 M1、M4
發表的數字比較，以及和作業系統回報的快取大小比較（L1 量到 128 KiB，系統也說 128 KiB）。

**10. 這個專案有什麼限制？**
看不到微指令和連接埠，單元數是推論的。整數和浮點暫存器之間的延遲只能量「來回」的總和，拆不開。
記憶體相關的實驗在共用機器上比較不穩，所以標了信心度。指標驗證指令在一般行程裡金鑰沒啟用，量到的是「沒作用」
的行為。SME 和 MTE 指令沒有涵蓋。這些都寫在 README 的「限制」裡，沒有假裝量到。

**11. 別人送來的資料，你怎麼知道是真的？**
老實說，沒辦法百分之百知道。自動檢查擋得住失誤和粗糙的竄改：統計值一定要能從原始數字重算出來、錨點要成立、
P 核不能比 E 核小、跟同一顆晶片的舊資料不能差太多。但如果有人很用心地捏造一份處處合理的假資料，任何自動檢查都
分辨不出來。真正的防線是「同一顆晶片要有多份獨立的提交而且一致」，所以網站會顯示每顆晶片有幾份資料、每份從哪個
issue 或 pull request 來，兩份獨立資料一致才標成 verified。離群值的門檻也是用真資料校準的：把 M5 自己的五輪拆兩組
互相比，正常的雜訊最多讓 0.06% 的數字超出規則，所以超過 0.5% 才標記整份提交。

**12. 讓陌生人觸發 GitHub Actions，不怕被入侵嗎？**
有三個重點。第一，issue 內容只當資料讀：Python 從事件檔讀進來解析成 JSON，從不執行，也從不把它塞進 shell 指令
（有測試檢查每個 workflow 的 `run:` 裡沒有 `${{ }}`）。第二，最小權限：解析資料的那一段只有唯讀權限，能寫入的
那一段只處理檢查程式自己產生的檔案，而且只推到 `submission/issue-N` 分支，絕不碰主分支，合併一定是人來按。
第三，pull request 的檢查雖然用 `pull_request_target`（才能留言），但只 checkout 主分支的程式，PR 裡的檔案只用
`git show` 當資料讀。第三方 actions 也都釘在完整的 commit SHA，避免被換掉。

## 六、如果只能記三句話

1. 系統本來就替每條執行緒記「週期數」和「指令數」，而且分大小核心，所以不用 root 也能量。
2. 每個數字都是「跑 n 圈和 2n 圈相減」，而且只採用指令數完全正確、沒有換核心的那幾次。
3. M5 會預測資料，傳統的量法會被騙；這個工具故意讓資料無法預測，並且把「它會預測」這件事本身也量出來。

（第四句，講到提交平台時用：任何人 `make submit` 貼進 issue 就能送資料；送的是每輪原始數字，
檢查程式會重算一次，對不上就退回；但真正的防線是多份獨立提交互相印證。）
